# All About Turns and Messages

This guide explains how **RACHEL** (**R**pg **A**gent **CH**at **E**valuation **L**oop) processes message payloads, structures upstream calls, resolves turn numbers, and differentiates between turn keys and turn numbers.

---

## 1. Message Types & Processing Flow

RACHEL operates as a stateful proxy between an external roleplay client (like JanitorAI or SillyTavern) and upstream LLM completion providers. It handles two distinct message sequences:

### A. Incoming Messages
These are the messages sent by the client interface to RACHEL in the `/v1/chat/completions` API payload. They represent the chronological chat history:
- **System / Developer Prompts**: Initial context settings or character description cards.
- **User Messages**: Prompts written by the player.
- **Assistant Messages**: Narrations generated by the AI.

### B. Outgoing Messages
These are the modified messages that RACHEL submits to the upstream LLM (via OpenRouter, OpenAI, etc.). To comply with strict LLM API contracts (like Gemini or Anthropic), RACHEL refines the incoming payload:
1. **User-Merged Directives (Round 1)**: RACHEL does not append a trailing system message for its dynamic instructions (state values, secret states, planning checklists, and sandbox rules). Doing so violates the alternating role constraint (user-assistant-user) or trailing developer message restrictions of modern LLM APIs. Instead, in Round 1, RACHEL **injects/merges** its directives block directly into the content of the *final user message* of the turn, delimited by separators:
   ```text
   [Original Player Message content]

   ---
   [RPG DIRECTIVE & GAME STATE (Turn X)]
   [Dynamic System Instruction]
   ```
   This constructed user message is cached in the turn context (`cached_constructed_user_message`). This prevents alternation errors and maximizes LLM prompt prefix cache efficiency across multi-round completions.
2. **Chronological Tool Sequence & State Snapshot Expansion (Rounds 2+)**: When the LangGraph loop runs, if the LLM emits a tool call (`execute_code_sandbox`), RACHEL executes the sandbox, captures the output, and appends the assistant's tool-call message and the corresponding tool result message to the **Outgoing Messages** array in strict chronological order:
   - **User Message Stability**: The user message in Round 2+ uses the cached constructed user message from Round 1 bitwise identically without re-injecting or modifying it.
   - **No Synthetic User Messages**: RACHEL strictly avoids appending any synthetic `user` message after a `tool` message. The LLM responds directly to the `tool` message in accordance with standard tool-calling protocol.
   - **Tool Message Snapshot**: The `tool` message for `execute_code_sandbox` is expanded to include both the code's stdout and the updated game state snapshot:
     ```text
     <stdout or "(no output)">

     [Updated Game State]:
     State:
     { ... }

     Hidden State:
     { ... }

     Plan:
     [ ... ]
     ```
   This ensures the LLM is fully grounded with mutated variables without needing an extra user prompt. Subsequent iterations continue appending tool interactions to this array before the final assistant narrative is returned to the client.

## 2. Turn Number Resolution

A **Turn** in RACHEL represents a single user message + assistant reply pair in the public chat history. RACHEL automatically calculates the turn numbers for the entire incoming history using a robust backward-propagating algorithm (`resolve_turn_numbers`):

- **Turn 1**: Determined by the location of the *first user message* in the chat history.
- **Unmutable Initial Sequence (`num_messages_with_unmutable_turn_number`)**: 
  - RPG setups often start with system instructions or introductory assistant messages before the player's first input. 
  - If a user message starts at index 0, Turn 1 starts at index 0. 
  - If the first player (user) message starts at index 3, the initial messages at indices 0, 1, and 2 do not have a turn number assigned (`None`). Turn 1 starts at index 3.
- **Backward Iteration**: 
  Instead of resolving only the last message and subtracting 1 for each prior step (which fails under middle-out message trimming or consecutive same-role messages), RACHEL evaluates **every non-user message individually** by iterating backward from the end of the history:
  1. **Cache Lookup**: If the message contains a `turn_key`, it checks the database/session storage cache for the turn's `meta-data.turn_number`.
  2. **Annotation Parsing**: If it is a cache miss, it parses the `turn_number` directly from the text of the `[proxy: ... turn_number=X]` annotation block.
  3. **Message Count Fallback**: If neither is found (e.g. cold start), it counts the total number of user messages up to that message's index.
- **User Message Resolution**: 
  Once non-user messages are resolved, the user messages are filled:
  - For user message at index `k`, it copies the resolved turn number of the next non-user message (`k+1`).
  - If the user message is at the very end of history (a new player action), it takes the `last resolved turn + 1`.

## 3. Turn Key vs. Turn Number (Crucial Distinction)

While they sound similar, **Turn Key** and **Turn Number** serve completely different purposes in RACHEL's architecture:

| Attribute | Turn Number | Turn Key |
| :--- | :--- | :--- |
| **What it is** | An integer index (e.g. `1`, `2`, `3`). | A unique 24-character hexadecimal identifier (e.g. `abcdef123456...`). |
| **Purpose** | Tracks narrative progression and triggers periodic events (summaries, plans). | Identifies a specific *execution instance* of the state cache. |
| **Uniqueness** | Shared by all retries/swipes on the same turn. | Unique to each swipe, retry, or message edit branch. |
| **Branching** | If you swipe/retry Turn 5 three times, the Turn Number remains `5`. | Each of the three swipes generates a unique Turn Key to save states separately. |

### Why this matters
Roleplay users frequently "swipe" or "retry" assistant replies to get a better narrative branch. If RACHEL stored game states indexed only by **Turn Number**, retrying Turn 5 would overwrite the state of the first attempt, corrupting the inventory/HP if the user swiped back. 

By indexing state saves by **Turn Key** (embedded in assistant annotations as `[proxy: session=xxx turn=turn_key turn_number=turn_number]`), RACHEL isolates each conversation branch. Swiping back or editing a previous message automatically re-loads the exact Turn Key and restores the correct historical state branch.
